# Коміт 1: `fast writes, load data, shard outage, delete`

Файли: `backend/`, `tests/` (крім `test_operations.py` і `test_load_tools.py`), ця нотатка. Після коміту: 168 тестів проходять, 18 пропущено (потрібні живі БД або стенд).

Числа нижче зняті на тимчасовому кластері (MacBook Air M2, 3 шарди, MongoDB 8.3, без Docker). Для звіту вони не годяться, лише для порівняння «було / стало».

## 1. Швидкий запис

| Було | Стало | Навіщо |
|---|---|---|
| ~200 запитів на батч зі 100 документів | 1 `find` + 1 `insert_many` | головне гальмо: ~1 000 док/с |
| Один лічильник на scope | 64 слоти `<scope>#NN`, при читанні сумуються | паралельні транзакції конфліктували: 4 консюмери були повільніші за 1 |
| Батч ≤ 100, обробка по одному | Батч до 1000 (типово 500), 4 транзакції паралельно | більше документів на одну двофазну фіксацію між шардами |
| `replay_outbox` зберігає тексти | зберігає посилання `{snapshot, hash, start, end}` | до ~27 ГБ зайвого на 9 млн документів (розрахунок) |
| Checkpoint перебирає всі завершені батчі | індекс `WHERE status <> 'completed'` | на 90 000 батчів: 7,35 мс стало 0,014 мс |
| Темп 10–5000 | 10–100 000 або `0` = MAX | «максимальна швидкість» |

Разом: ~1 000 → ~20 000 док/с. Гарантії ті самі: одна транзакція, snapshot read, majority write, квитанція батча.

Де дивитися:
- `content_service/infrastructure/database/corpus_repository.py` → `persist_batch`, `counter_id`
- `content_service/infrastructure/messaging/runtime_broker.py` → `consume`, `_process`
- `content_service/worker.py` → ролі `consume` / `dispatch`, `dispatch_once`
- `ingestion_service/infrastructure/database/replay_store.py` → `produce`, `materialize`, `dispatch`, `next_production`
- `migrations/002_partitioning.sql`, `003_high_load.sql`

## 2. Дані `load-cs`

Документ рахується з `(job, номер)`, файлів на диску немає. Основа: 4000 рядків `synthetic-cs`, змінюються матч, дата і статистика гравців.

- **ID:** `load-cs` має UUIDv8, що росте з номером (вставка в край B-дерева). `load-cs-random` має випадкові ID, це для порівняння в E1.
- **Навіщо детермінованість:** повторна доставка дає той самий документ, а перевірка втрат просто перераховує ID.
- **Ізоляція:** у звичайний перегляд, map-reduce `all` та Elasticsearch не потрапляє.

Де дивитися: `contracts/load_ids.py`, `ingestion_service/infrastructure/datasets/load_generator.py`.

## 3. Втрата шарда

- Збій кластера (`StoreUnavailable`) відділено від битих даних: батч іде назад у чергу, спроба не витрачається. Раніше після 5 спроб job ставав `failed`.
- Спроба обмежена 20 с. Без цього драйвер висів 120 с, хоч який таймаут стоїть.
- `/documents` без шарда віддає часткову відповідь (`degraded: true`), раніше 503.
- `/api/v1/cluster/status` показує, який шард живий.

SIGKILL під час запису 120 000 документів (RabbitMQ замінено тестовим двійником):

| Шард | Без шарда | Втрачено | Запис відновився через |
|---|---|---|---|
| звичайний | 25 с | 0 | 1,3 с |
| первинний для бази | 25 с | 0 | 0,9 с |
| звичайний | 11 хв | 0 | 1,5 с |

Де дивитися: `availability.py`, `cluster_status.py`, `corpus_maintenance.py` → `verify`.

## 4. Видалення

- `purge`: відсоток, кількість або один job. Лише `load-cs`, документи й лічильник в одній транзакції.
- `reset`: усе, включно з реальним корпусом; колекція створюється і шардується заново.
- `compact`: повертає місце ОС після часткового видалення.
- Квитанції батчів при `purge` лишаються, тому повторна доставка не воскресить видалене.
- `ingestion_service.manage`: `jobs`, `cancel`, `purge-jobs`.

## Слабкі місця

- Поки шарда немає, запис **стоїть повністю**: кожен батч зачіпає всі шарди, реплік немає.
- Нові документи `load-cs` **не шукаються** через Elasticsearch. Якщо на захисті попросять знайти щойно записаний документ пошуком, не вийде.
- Якщо вимкнений шард первинний для бази, статистика теж недоступна.
- Не перезапускати `content_api` і worker під час збою: при старті вони створюють індекси, і без шарда це, найімовірніше, не вдасться (не перевіряв).
- Якщо коміти самі по собі довші за 20 с, батчі підуть по колу. На прогонах стежити за логом `Store unavailable`.
- У скасованого job «у черзі» лишається більше нуля, бо рахуються невідправлені батчі. Лише вигляд.
- Після `purge` команда `verify` покаже «втрати» для цього job, і це правильно.
- Тексти `load-cs` схожі між собою, тож стискаються трохи краще за реальні: 1,7 КБ на документ може бути оптимістично.

5. Чому після SIGKILL `estimatedDocumentCount` бреше, а дані цілі?
