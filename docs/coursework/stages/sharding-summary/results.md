# Шардований кластер MongoDB, 3 шарди (пункт 4 плану)

Дата: 19.11.2026. Локальний Docker Desktop (Windows 11), MongoDB 7.0.48, один хост. Проєкт Compose `cs-sharded` має окремі томи. Основний стек `cs-coursework` зупинено командою `docker compose stop`. Його томи не змінювалися.

## Топологія

| Компонент | Контейнер | Replica set | Порт |
|---|---|---|---|
| Config server | `cfg1` | `cfgRS` (configsvr) | 27019 |
| Шард 1 | `shard1` | `shard1RS` | 27018 |
| Шард 2 | `shard2` | `shard2RS` | 27018 |
| Шард 3 | `shard3` | `shard3RS` | 27018 |
| Маршрутизатор | `mongos` | — | 27017 |

- Content підключається лише до `mongodb://mongos:27017/`.
- Кожен replica set має одного учасника. Це демонстрація розподілу даних, а не відмовостійкості.
- Ініціалізацію виконує `deploy/mongo-sharded-init.sh`. Скрипт ідемпотентний і робить таке:
  1. `rs.initiate` для 4 наборів;
  2. `sh.addShard` для трьох шардів;
  3. `chunksize = 2 MB`;
  4. `sh.enableSharding("content")`;
  5. `createIndex({_id: "hashed"})`;
  6. `shardCollection("content.source_documents", {_id: "hashed"}, numInitialChunks: 12)` на порожній колекції.

  Попереднє розбиття дає 12 чанків, по 4 на кожен шард, ще до першої вставки.
- `committed_batches`, `corpus_counters` і `outbox` не шардуються. Вони лежать на первинному шарді бази `content`.
- Транзакція батчу є розподіленою: документи потрапляють на 3 шарди, а лічильник і outbox — на первинний шард. Код Content не змінювався.

## `getShardDistribution()`

| Шард | Документів | Частка документів | Дані | Частка даних | Чанків |
|---|---:|---:|---:|---:|---:|
| shard1RS | 33 457 | 33,45 % | 98,84 MiB | 33,44 % | 4 |
| shard2RS | 33 123 | 33,12 % | 97,88 MiB | 33,12 % | 4 |
| shard3RS | 33 420 | 33,42 % | 98,79 MiB | 33,43 % | 4 |
| **Разом** | **100 000** | | **295,52 MiB** | | **12** |

- Відхилення від рівного розподілу менше ніж 0,7 відсоткового пункту.
- Хеш UUIDv5 рівномірно розкидає документи. Тому балансувальнику (увімкнено, режим `full`, 53 раунди) не довелося переносити чанки.
- У MongoDB 6.0+ автоматичного розбиття чанків за розміром немає. Чанки діляться лише тоді, коли балансувальник виявляє дисбаланс. Тому число чанків лишилося 12 (≈ 24,6 MiB на чанк), хоча `chunksize = 2 MB`. Розподіл по всіх шардах гарантує саме попереднє розбиття.
- **Повторна перевірка 19.11.2026 (фінальна верифікація).** `getShardDistribution()` показує ті самі документи й обсяги (33 457 / 33 123 / 33 420, 295,52 MiB), але **3 чанки, по одному на шард**. Це штатна робота AutoMerger MongoDB 7.0: суміжні чанки одного шарду об'єднуються у фоновому режимі. Документи між шардами не переносилися; точковий `find({_id})` і далі має стадію `SINGLE_SHARD`.

## `explain("executionStats")` через mongos

| Запит | Стадія mongos | Шардів | План на шарді | Ключів / документів переглянуто | Повернуто |
|---|---|---:|---|---:|---:|
| `find({_id: "004e262a-…"})` | `SINGLE_SHARD` | 1 (shard2RS) | `IDHACK` | 1 / 1 | 1 |
| `find({corpus_scope: "synthetic-cs", "metadata.document_type": "map"}).sort({_id: 1}).limit(20)` | `SHARD_MERGE_SORT` | 3 | `LIMIT > PROJECTION_SIMPLE > FETCH > SHARDING_FILTER > IXSCAN(corpus_scope_1_metadata.document_type_1__id_1)` | 60 / 60 | 60 → 20 |
| `count` з тим самим фільтром | `SHARD_MERGE` | 3 | `COUNT > SHARDING_FILTER > IXSCAN(…)` | 14 408 + 14 339 + 14 490 = 43 237 / 0 | 43 237 |

Висновки:

- **Точковий запит за ключем шардування.** `mongos` обчислює хеш `_id` і надсилає запит лише на шард, якому належить відповідний чанк (targeted query).
- **Фільтр за `corpus_scope` / `metadata.*`.** Ці поля не містять ключа шардування, тому запит іде на всі 3 шарди (scatter-gather).
  - Кожен шард використовує свій локальний складений індекс.
  - `mongos` зливає відсортовані потоки за `_id`.
  - Для `limit(20)` кожен шард повертає до 20 документів. Тому `mongos` отримує 60 документів і відкидає зайві.
- `SHARDING_FILTER` відкидає документи-сироти, яких шард не володіє. Під час міграції чанків це гарантує коректний результат.
- Ключ `{_id: "hashed"}` добре підходить для рівномірного запису та читання за ID. Списки й статистика (`/documents`, `/corpus/statistics`) завжди виконуються як scatter-gather.

## Файли доказів

- `evidence.json`: топологія, кількості за scope і типом, лічильники, чанки і `$collStats` по шардах, повні `explain`. Генерує `tools/sharding/collect_evidence.js`.
- `getShardDistribution.txt`, `sh-status.txt`: «сирий» вивід mongosh.
- `replay-jobs.json`: підсумок двох replay-задач з Ingestion API.

## Відтворення

```sh
docker compose stop                      # основний стек; без -v
docker compose -f deploy/docker-compose.sharded.yml --env-file .env up --build -d
# UI http://localhost:8082 → імпорт kaggle-cs і synthetic-cs
docker compose -f deploy/docker-compose.sharded.yml --env-file .env exec -T mongos \
  mongosh content --quiet --eval "$(cat tools/sharding/collect_evidence.js)" > evidence.json
```
