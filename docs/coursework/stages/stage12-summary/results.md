# Етап 12 — UI та наскрізний сценарій

Реалізовано корпус із пошуком і фільтрами, повну картку документа, операторський вхід та моніторинг імпорту. Читання: React → FastAPI → CorpusController → CorpusQueryService → CorpusStore/MongoCorpusRepository → MongoDB і назад.

## Додаткова перевірка та оформлення 18 листопада 2026 року

- Оновлено картку документа: окремі підсумок і статистика, незмінний оригінальний текст, розгортні технічні дані з українськими назвами, доступна назва діалогу, повернення фокуса та закріплена кнопка закриття. Збільшено читабельність, додано скидання фільтрів, підказку для точних назв, українські повідомлення помилок і пагінацію історії імпорту.
- Перевірено Chrome та Edge, мобільний viewport 390 × 844, клавіатуру, помилковий токен і заборону дробового темпу. Axe-core не знайшов порушень WCAG 2 A/AA та 2.1 AA у перевірених станах. Доказ: `ui-polish-check.json`. Це автоматичний аудит окремих станів, а не сертифікація доступності; фізичні телефони та скринридер не перевірялись.
- Переформатування перевірено на всіх 20 675 документах: після нормалізації пробілів текст повністю збігається; секція оригіналу показує збережений текст без перетворення (`tests/acceptance/verify_document_text.cjs`).
- На окремому Compose-проєкті `cs-acceptance` зі свіжими томами й тестовим піднабором **1 000 документів** пройдено SIGKILL обох workers, відключення RabbitMQ, два конкурентні імпорти, конкурентне створення з одним ключем та конфлікт двох команд паузи. Доказ: `resilience-check.json`.
- Виявлено й виправлено нескінченну повторну обробку некоректного JSON у failure callback. Три пошкоджені повідомлення (некоректний JSON, JSON-масив, об’єкт без ідентифікаторів) із некоректним retry header перевірено на реальному RabbitMQ: кожне завершило п’ять спроб і потрапило в DLQ. Підтвердження реального незавершеного пакета переміщено у DLQ та відновлено штатною командою redrive. Окремо перевірено корельований пакет з порожнім заголовком: після повторів завдання стало failed; новий replay успішно завершився без нових документів (`failed-job-check.json`).
- Реальні відключення MongoDB/PostgreSQL повертають HTTP 503; UI показує українську помилку та відновлюється після запуску БД. На 21 додатковому призупиненому тестовому завданні перевірено другу сторінку історії. Доказ: `ui-outage-check.json`.
- `mongodump/mongorestore` і `pg_dump/pg_restore` відновили копії повного основного стенда в окремі БД `restore_acceptance`: **20 675 документів**, узгоджений лічильник, **3 завдання**, суми **20 675 нових / 41 350 повторних** записів. Основні БД не перезаписувались. Доказ: `backup-restore-check.json`.
- Після виправлень повторно пройдено **35 тестів** на контейнерних БД; повний інтеграційний тест попереднього запуску наведено нижче. Збірка TypeScript/Vite успішна. DOCX оновлено фактами перевірок і новими скриншотами; таблицю змісту перераховано, документ відрендерено для візуальної перевірки.

Тести з відмовами виконані на ізольованому піднаборі; повний імпорт 20 675 документів перевірено окремо. Результати не є навантажувальним тестуванням, перевіркою втрати диска чи доказом кластерної відмовостійкості.

## Перевірено на Docker Compose 17 листопада 2026 року

- `docker compose deploy/config --quiet` та збірка/запуск повного стенда пройдені.
- 35 архітектурних, прикладних і repository-тестів пройдено всередині Linux-контейнера з реальними MongoDB/PostgreSQL; інтеграційний тест виконано окремо, також успішно (325,49 с).
- Повний CSV → JSONL → PostgreSQL outbox → RabbitMQ → MongoDB → API сценарій зберіг **20 675 нових документів**. Один некоректний CSV-рядок відхилено під час підготовки.
- Повторний імпорт: **0 нових, 20 675 дублікатів, backlog 0**. Підтверджена контрольна точка обох завдань — 20 675.
- Перевірено темп 10 → 500, паузу/продовження, перезапуск обох workers під час імпорту та збереження даних і прогресу після перезапуску MongoDB/PostgreSQL.
- Пошук, фільтри, різні сторінки, порожній результат, 404, валідація розміру сторінки та буквальне трактування `.*` пройдені через Nginx/API.
- Фактичні `countDocuments` та транзакційний лічильник MongoDB збігаються: 20 675.
- Машиночитані результати: [compose-check.json](compose-check.json). Інтеграційний тест: `tests/test_stack_integration.py`.
- Playwright на реальному Compose-стенді без HTTP-заглушок перевірив корпус, картку документа, порожній пошук, операторський вхід, запуск імпорту, паузу, темп 10 → 500 і продовження до завершення. Результат: [compose-browser-check.json](compose-browser-check.json); скриншоти: `ui-corpus.png`, `ui-document.png`, `ui-import.png`. JavaScript-помилок не зафіксовано.
- Один уже оброблений пакет і його підтвердження надіслано через RabbitMQ ще по два рази. Кількість документів, транзакційних квитанцій і показники всіх завдань залишилися незмінними; усі чотири черги порожні. Доказ: [compose-redelivery-check.json](compose-redelivery-check.json).

Виправлено виявлену на першому запуску помилку CRLF у `deploy/postgres-init.sh`; `.gitattributes` задає LF для shell-скриптів. Значення 500 є цільовим темпом, а не гарантією фактичної пропускної здатності. Тест не є навантажувальним дослідженням чи демонстрацією відмовостійкого кластера.

## Попередні локальні перевірки

- 35 тестів пройдено з увімкненими реальними PostgreSQL і MongoDB; один повний Compose-тест пропущено.
- Окремий тест на справжньому ізольованому PostgreSQL пройдено: міграції, ідемпотентність, pause/resume, темп, outbox, переставлені підтвердження, контрольні точки й помилки.
- TypeScript та production-збірка Vite пройдені.
- Playwright із явно заданими HTTP fixtures: desktop/mobile, картка документа, порожній пошук, авторизація оператора, зміна темпу та пауза — пройдено. Це перевірка UI, не доказ роботи реальної MongoDB.

- На справжньому MongoDB 7.0.14 перевірено транзакції, повторні пакети, повторні документи, rollback, фільтри й статистику.
- У тимчасову MongoDB через command service записано всі 20 675 документів; фактичну кількість звірено з транзакційним лічильником. RabbitMQ у цій перевірці не використовувався.
- React → Content API → контролер → сервіс → repository → справжня MongoDB: список, картка, порожній пошук і перевірка пагінації пройдені без перехоплення HTTP. Доказ попередньої перевірки — `native-browser-check.json`; поточні скриншоти вже оновлено зі стенда Compose.

## Повна демонстрація на Docker-стенді

1. Запустити Compose, увійти з операторським токеном і почати імпорт зі швидкістю 10 документів/с.
2. Показати зростання підтверджених записів, змінити темп на 500, призупинити й продовжити завдання.
3. Знайти команду, застосувати фільтр карти, відкрити документ із текстом та походженням.
4. Повторити імпорт: нових документів немає, лічильник дублікатів зростає.
5. Перезапустити workers посеред імпорту та бази після завершення; звірити кількість документів і збережений прогрес.
6. Виконати `RUN_STACK_TESTS=1` інтеграційний тест з README.

Попереднє обмеження через відсутність Docker Engine усунено. Інтеграційний тест надалі залишається opt-in, бо створює завдання й перезапускає контейнери.
